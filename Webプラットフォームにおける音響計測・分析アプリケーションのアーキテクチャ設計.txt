= \sqrt{\frac{1}{N} \sum_{i=1}^{N} x_i^2}$$この0.0から1.0の間の線形スケール上に存在するRMS値は、以下の標準的な対数式を使用して、フルスケールに対するデシベル（dBFS）に変換される。$$dBFS = 20 \log_{10}(\max(RMS, \epsilon))$$

LU低い値）を利用する。音声がこのしきい値を下回った場合（例：沈黙の瞬間）、アルゴリズムは積分を一時停止し、無音状態が全体のラウドネススコアを不当に引き下げるのを防ぐ。このアルゴリズムは、途切れることのない継続的な積分計算と、（スライディングウィンドウおよびゲーティングのための）過去のオーディオブロックのメモリ履歴を要求するため、前述の不連続なAnalyserNodeを使用して実装することは不可能である。代わりに、JavaScriptまたはコンパイル済みのWebAssemblyを使用して、AudioWorkletProcessor内に直接コーディングする必要がある。非推奨となったScriptProcessorNodeの現代的な後継であるAudioWorkletは、開発者が専用のオーディオレンダリングスレッド上で直接実行されるカスタムの音声処理コードを記述することを可能にする。AudioWorkletProcessorを利用することで、アプリケーションは音声ブロック（通常は1フレームあたり128サンプル）の継続的かつ途切れることのないストリームを受信する。これにより、フレームのドロップなしにすべての単一オーディオサンプルが確実に処理され、累積的な騒音暴露モニタリング、トゥルーピーク（True-Peak）計測、および放送規格のラウドネスアルゴリズムに必要とされる高精度で連続的な積分が可能となる。処理されたスカラー値（特定の128サンプルのブロックに対して計算されたデシベル値やLUFS値など）は、MessagePortを介してバックグラウンドのオーディオスレッドからメインのUIスレッドに送り返され、視覚化される。これにより、計算コストの高いDSPロジックがDOM操作や描画のオーバーヘッドから完全に分離される。現在では、libebur128やDOM Christie氏のneedlesなどのオープンソースライブラリがWeb環境に移植されており、これらの複雑な計算の統合を容易にしている。音声録音とローカルストレージへのエクスポート機能視覚的な波形表示や高度な数値分析に加えて、アプリケーションは音声を実際に録音し、モバイルデバイスのストレージに保存するというユーザーの主要な要件を満たす必要がある。この機能はMediaRecorder APIを使用して実行される。MediaRecorderは、getUserMediaから生じる元のMediaStream、またはAudioNodeの宛先（Destination）から出力される処理済みのストリームを受け取り、それを圧縮フォーマットにエンコードする機能を提供する。JavaScriptconst options = { mimeType: 'audio/webm; codecs=opus' }; 
const mediaRecorder = new MediaRecorder(stream, options);
録音が進行するにつれて、MediaRecorderはエンコードされたメディアデータのチャンクを含むdataavailableイベントを定期的に発行する。アプリケーションはこれらのチャンクを配列に蓄積していく。ユーザーの操作によって録音が停止されると、アプリケーションはこれらのチャンクを結合し、単一のバイナリBlobオブジェクトを生成する。モバイルブラウザおよびPWAにおけるファイルシステムのジレンマ生成されたこのBlobをモバイルオペレーティングシステムのネイティブなファイルシステムにエクスポートするプロセスは、デスクトップブラウザにおいては極めて単純であるが、モバイルデバイス、特にiOSのプログレッシブWebアプリ（PWA）環境においては、著しい摩擦と制約をもたらす。Webにおける標準的なダウンロードの仕組みは、オブジェクトURL（window.URL.createObjectURL(blob)）を作成し、それをdownload属性を持たせた非表示のHTMLアンカー（<a>）タグにアタッチして、プログラムから強制的にクリックイベントを発火させるという手法である。Android上のChromeでは、この手法は確実に機能し、デバイスのネイティブな「ダウンロード」フォルダへのファイルの保存をトリガーする。しかし、iOSにおける挙動は厳格に制限されている。AppleのWebKitエンジンは、セキュリティの管理を徹底し、開発者をネイティブのApp Store配信へと誘導する目的もあって、PWAに対して厳しい制限を課している。iOSでスタンドアロンのPWAとして動作している場合、従来のアンカータグを使用したダウンロードは、ネイティブの「ファイルに保存」という共有シート（Share Sheet）を表示することなく、サイレントに失敗するか、あるいはファイルへのアクセス機能が欠落した切り離されたWebViewを開いてしまうことが多い。さらに、iOS 18のSafariの最近のバージョンアップにおいては、Blobベースのダウンロードが、ユーザーが指定した「ファイル」アプリのフォルダに正常に保存されず、一時的なキャッシュに閉じ込められてしまうという既知のバグも報告されている。この重大な制約を回避するために、開発者は多くの場合、Web Share API（navigator.share()）を利用し、生成されたBlobをFileオブジェクトとしてAPIに渡す実装を行う必要がある。これにより、ネイティブのiOS共有シートが強制的に呼び出され、ユーザーが明示的に「ファイルに保存」を選択できるようになる。ファイルサイズやその他の制限によってFileオブジェクトの共有がOSに拒否された場合、開発者が最後に取れる手段は、BlobをBase64のData URIとして読み込み、それを新しいタブで開いて、ユーザーにブラウザのネイティブな保存機能を手動で操作させることである。これはユーザーエクスペリエンスの観点からは最適とは言えないが、現状のiOSプラットフォームの制限下においては不可欠なフォールバック機構である。バックグラウンド実行と電源管理の制約Webベースの音響モニタリングアプリケーションにとって最も致命的で克服困難な動作上の制約は、バックグラウンドでの実行能力の欠如である。本格的な騒音計や環境音モニタリングツールは、等価騒音レベル（$L_{eq}$）やインテグレーテッドLUFSを計算するために、数十分から数時間にわたって継続的に稼働させたまま放置されることが一般的である。しかし、モバイルオペレーティングシステムは極めてアグレッシブなリソース管理を実施している。バッテリー寿命を維持し、ユーザーのプライバシーを確保するために、AndroidとiOSの双方は、画面がロックされるかアプリケーションがバックグラウンドに移行した直後に、DOMの実行を容赦なく一時停止し、Web Audio APIのコンテキストを停止させ、マイクへのアクセス権限を無効化する。ネイティブアプリケーションを開発している場合、開発者はフォアグラウンドサービス（Android）を登録するか、バックグラウンドオーディオセッション（iOS）を構成することによって、OSのこの振る舞いを回避することができる。しかし、Webアプリケーションにはそのような特権は与えられていない。iOS上のPWAは、スマートフォンの画面がロックされている状態では、音声を録音したりDSP演算を実行したりすることはシステムレベルで完全にブロックされている。Screen Wake Lock APIによる回避策Webアプリケーションがバックグラウンドで動作できない以上、アーキテクチャ上の唯一の解決策は、デバイスがバックグラウンド状態に移行すること自体を完全に防ぐことである。これはScreen Wake Lock APIを利用して実装される。アプリケーションからnavigator.wakeLock.request('screen')を呼び出すことにより、モバイルOSの自動画面ディミング（暗転）および自動ロック機構を無効化するようシステムに要求することができる。これにより、画面が強制的にオンの状態に保たれ、結果としてDOMはアクティブな状態を維持し、マイクストリームも途切れることなく継続される。ただし、Wake Lock APIはドキュメントの可視性（Visibility）状態と厳密に結びついている点に注意が必要である。ユーザーが手動で別のタブに切り替えたり、ブラウザ自体を最小化したりすると、OSは即座にWake Lockを解除し、オーディオ処理はクラッシュするかサスペンド状態に陥る。したがって、アプリケーションはvisibilitychangeイベントのリスナーを実装しなければならない。ユーザーがアプリケーションに戻った場合、コードは再びWake Lockを要求し、停止したAudioContextの再開（Resume）を試みる回復ロジックを備えている必要がある。結論として、これらのシステム上の制約により、Webアプリケーションはフォアグラウンドでの利用に根本的に制限されており、ポケットに入れたまま機能するノイズドジメーター（騒音曝露計）のような使い方はアーキテクチャ上不可能である。ユーザーインターフェースには、正確な測定を続けるためには画面を開いたままにしておく必要があることを明示するガイダンスを組み込むことが推奨される。結論Web APIのアプローチを通じて、スマートフォンからアクセス可能な、録音、オシロスコープ波形表示、A/C特性による騒音測定、およびLUFSなどの高度な指標算出を備えた包括的な音響測定アプリケーションを構築するという命題は、技術的に十分に実現可能である。最新のブラウザエンジンは、WebRTCによる不要な音声最適化を制約パラメーターを通じて無効化することで、クリーンな生の音声データを取得する能力を提供している。また、AnalyserNodeを用いた高速なリアルタイム波形描画から、AudioWorklet内で動作するWebAssemblyやJavaScriptによるサンプル単位の厳密な数学的積分（LUFS等）まで、あらゆるデジタル信号処理をクライアントサイドのみで完結して実行することができる。しかしながら、このアーキテクチャは物理的なキャリブレーションの絶対的精度と、バックグラウンド動作の持続性という2点において、プラットフォームの限界に直面する。モバイル端末ごとにマイクのハードウェア感度が大きく異なるため、法的効力を持つような絶対的なSPL（音圧レベル）測定を行うには、外部の校正機器を用いた手動の疑似キャリブレーション機能の組み込みが不可欠となる。また、iOSを中心としたPWAのファイル保存に関する制約への対処（Web Share APIの活用）や、Screen Wake Lock
